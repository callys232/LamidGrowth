[0071] 01CANONICAL OPERATING DOCTRINE
[0072] The invariant model every agent, engine and tool must preserve.
[0073] 1.1 Category and operating model
[0074] The public category is the Continuous Human-AI Growth Operating System.
[0075] The universal public operating cycle is Clarity -> Capability -> Consistency. Growth is the outcome.
[0076] Continuous Intelligence continuously interprets permitted changes and refreshes understanding.
[0077] Persistent Progression allows permitted context, intelligence and already-authorized work to advance across time and between user interactions.
[0078] Human Control preserves authority: no permission expands itself, and consequential action pauses unless exact authority has been explicitly delegated under policy.
[0079] PUBLIC TRUST PRINCIPLEProgress keeps moving. Control stays with you.
[0080] 1.2 Three progression lanes
[0081] Lane
[0082] What may progress
[0083] Authority rule
[0084] Context Progression
[0085] Authorized connected data, project state, metrics, files, signals and status may synchronize or refresh.
[0086] Observational authority only; does not imply action authority.
[0087] Intelligence Progression
[0088] Analysis, forecasts, relevance, risk, opportunity, recommendations and confidence may be recalculated as permitted inputs change.
[0089] Analysis may evolve; it does not grant approval or commitment authority.
[0090] Authorized Work Progression
[0091] Scheduled or already-approved workflow steps may continue within explicitly defined scope.
[0092] Scope is fixed, revocable, traceable, interruptible and non-expanding.
[0093] 1.3 Authority bands
[0094] Band
[0095] Examples
[0096] Default gate
[0097] A1 - Observe & Update
[0098] Read, ingest, synchronize, recalculate, detect changes, refresh state.
[0099] No new approval when valid read/update permission exists.
[0100] A2 - Progress Within Authorization
[0101] Continue approved workflow, perform scheduled analysis, notify assigned participants, update an existing plan state.
[0102] Execution-time permission re-check; pause on scope ambiguity or policy failure.
[0103] A3 - Consequential Commitment
[0104] Commit funds, enter agreements, publish externally, materially change strategy, change permissions, irreversible actions.
[0105] Explicit human approval or exact predelegated authority under enforced policy; step-up/dual approval where required.
[0106] 02AGENT RUNTIME & AUTHORITY CONTRACT
[0107] Delegated execution without unbounded autonomy.
[0108] 2.1 Agent definition
[0109] A LAMID ONE agent is a bounded runtime actor that reasons over authorized context, selects registered tools, and performs or recommends actions within an explicit task, identity, scope, policy, risk, budget, time and evidence envelope. An agent is never a source of authority by itself.

[0111] Field
[0112] Required contract

[0117] objective

[0122] Allow-listed Tool Fabric tool IDs and schemas only.

[0127] risk_budget

[0129] human_gate

[0131] time_boundary
[0132] Start, expiry and stop conditions.
[0133] evidence_policy

[0135] memory_policy

[0137] rate_cost_policy

[0139] audit_contract
[0140] Inputs, reasoning summary, tools, outputs, approvals, mutations and outcomes logged.
[0141] revocation
[0142] Immediate stop/revocation path as technically practicable.
[0143] rollback
[0144] Rollback, restoration or compensating action where possible.
[0145] 2.3 Runtime lifecycle
[0146] Resolve principal and tenant -> load objective and scoped context.
[0147] Classify intent, engine affinity, tool candidates and risk.
[0148] Evaluate authorization/policy before every sensitive read or action.
[0149] Reason using deterministic services, retrieval and approved models.
[0150] Select tools from typed manifests; reject tools outside allow-list or authority band.
[0151] Pause for Human Control gate whenever policy, confidence or consequence requires it.
[0152] Execute idempotently; use replay protection, retries and compensation rules.
[0153] Observe outcome and update only permitted workflow/context state.
[0154] Generate return-state summary: progressed, changed, improved, reassessed, paused/blocked, needs human judgment.

[0374] 3.1 Agent composition rules
[0375] Agents are reusable runtime roles, not standalone public products.
[0376] A compound workflow may instantiate multiple agents; one orchestration trace must preserve correlation and authority lineage.
[0377] An agent may invoke tools from multiple engines when the objective requires it, but tool permissions and policy are evaluated independently.
[0378] Agent memory is scoped by tenant/workspace/object and purpose; no cross-tenant or hidden cross-workspace memory.
[0379] Agent recommendations must expose evidence, material assumptions, uncertainty and approval state where consequential.
[0380] Agents must not bypass deterministic verification, financial controls, KYC, access controls or human approval through model output.

[0407] 4.1 Core operating loop
[0408] Component
[0409] Contract responsibility
[0410] 1. Sense

[0419] Select and call one or more registered tools using typed manifests and policy gates.

[0421] Execute authorized internal or external actions with idempotency, replay protection and transaction boundaries.
[0422] 7. Observe
[0423] Capture completion, status changes, user decisions, external events and measurable outcomes.
[0424] 8. Learn
[0425] Update permitted contextual state, reusable knowledge, performance signals and workflow state.
[0426] 9. Explain
[0427] Expose evidence, assumptions, confidence, decision trace and material automated actions.
[0428] 10. Govern
[0429] Apply identity, authorization, approval, privacy, security, risk, budget and human-override controls throughout the lifecycle.

[1880] 13.2 Mapping rules
[1881] The mapping above is an allow-list baseline, not a blanket grant. Actual invocation is narrowed by user/tenant policy, object scope and task context.
[1882] Cross-engine tool use is permitted when declared by the Tool Manifest and agent allow-list.
[1883] Agent-to-tool permissions are versioned and testable; changes require architecture/security review for R3/R4 tools.
[1884] Financial, identity, KYC, permission and externally binding tools always use server authority and risk-appropriate human gates.
[1885] 14SECURITY, TRUST & ABUSE PREVENTION
[1886] Controls apply to every agent, engine, tool, workflow, connector and progression lane.
[1887] Threat / failure mode
[1888] Mandatory control
[1889] Phishing / account takeover
[1890] Passkeys/WebAuthn where available, MFA/step-up, session/device risk, recovery protection, sensitive-action reauthentication.
[1891] BOLA/IDOR/BFLA / privilege escalation
[1892] Server-side object/function/property authorization, tenant isolation, deny-by-default policy, test matrices.
[1893] Permission drift / agent overreach
[1894] Principal-bound delegation, non-expanding permissions, execution-time re-check, explicit tool allow-lists, revocation.
[1895] Rate/resource abuse
[1896] Per-identity, tenant, IP, tool, model and sensitive-flow limits; budgets, queues, circuit breakers, backpressure.
[1897] KYC / verification bypass
[1898] Server-authoritative state, evidence integrity, anti-replay, provider verification, no client/model self-attestation.
[1899] Prompt injection / tool abuse
[1900] Untrusted content separation, retrieval provenance, tool schema allow-lists, action confirmation, connector egress policy.
[1901] File/upload attacks
[1902] Type/size/content validation, malware quarantine, archive-bomb protection, safe parsing, SSRF-safe fetching.
[1903] Webhook/replay spoofing
[1904] Signature verification, timestamp windows, nonce/idempotency, source allow-list, event correlation.
[1905] Financial duplicate/unauthorized release
[1906] Append-only ledger, idempotency, reconciliation, step-up/dual approval, release-state machine, provider verification.
[1907] Silent background autonomy
[1908] Observable progression lanes, stop/expiry conditions, return-state reporting, audit, pause/revoke/override, Human Control gates.
[1909] Cross-tenant memory leakage
[1910] Tenant/workspace-scoped retrieval, row/object authorization, provenance, retention policy, deletion handling.
[1911] Supply-chain / model/provider risk
[1912] Pinned dependencies, SBOM, secure SDLC, provider/model registry, versioned prompts/evals, fallbacks and incident response.
[1913] NON-NEGOTIABLENo autonomous component may silently increase its role, data access, tool access, spending authority, external communication authority or workflow permissions.
[1914] 15ACCEPTANCE & GOVERNANCE
[1915] Definition of done for agents, engines and the Tool Fabric.
[1916] Acceptance domain
[1917] Minimum evidence
[1918] Architecture
[1919] Every capability maps to an approved engine/shared plane, workspace and tool manifest; no competing top-level engine model.
[1920] Agent safety
[1921] Every agent has principal, objective, allow-listed tools, data scope, max authority, risk/cost policy, human gate, expiry, audit and revocation.
[1922] Persistent Progression
[1923] Context, Intelligence and Authorized Work lanes can progress, pause and revoke independently; no lane infers authority from another.
[1924] Authorization
[1925] Cross-tenant/object/function/property/action bypass suites pass; server-side checks apply at execution time.
[1926] Tool Fabric
[1927] All 202 registry items have stable IDs before production implementation, typed schemas, engine affinity, visibility, risk class and version lifecycle.
[1928] Evidence
[1929] Material recommendations and verification results expose evidence, assumptions, uncertainty/confidence and human-review state.
[1930] Commercial assurance
[1931] Proposal -> structured agreement -> deliverable -> criterion verification -> human approval -> controlled release -> reconciliation is demonstrated without duplicate release.
[1932] Security
[1933] Phishing, authz bypass, rate abuse, SSRF, upload, webhook/replay, KYC, payment and AI/tool-abuse tests pass at risk-appropriate depth.
[1934] Observability
[1935] Agent/tool/workflow traces, audit events, metrics, alerts and return-state reports are queryable and tenant-safe.
[1936] Human Control
[1937] Authorized humans can inspect, redirect, pause, revoke and override progression; consequential action gates behave exactly as configured.
[1938] Experience
[1939] Public UI preserves progressive disclosure; no tool wall, no competing public engine products, and Growth remains expressed as outcome.
[1940] Change control
[1941] Agent/tool/engine contract changes are versioned, reviewed, migration-safe and traceable to ADR/change request.
[1942] 15.2 Change rule
[1943] New capability enters LAMID ONE through the Tool Fabric, an approved workflow/workspace, a bounded agent role, or a shared service. A new public module, new top-level engine, or broader authority model requires explicit architecture and product-governance approval; feature growth must not recreate taxonomy sprawl.
